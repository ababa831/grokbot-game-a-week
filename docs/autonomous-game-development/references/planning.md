# 企画・ゲーム設計リファレンス（Planning & Architecture）

YouTube「桜井政博のゲーム作るには」に基づく企画・設計の8大原則。
企画立案、コンセプト固定、機能追加の判断、仕様書の作成、プロトタイプ検証時に参照する。

---

### #01 企画書は1枚で（ペラ1枚の原則）
- **核心**: 企画書は分厚く書かない。ゲームの核、画面構成、プレイヤーが体験する面白さを1枚（A4ペラ1枚または1画面）に凝縮できなければ、その企画は整理されていない証拠。
- **Core Skill**: **ワンシート・スコープ定義（Single-Sheet Architecture）**
- **AIへの実装・指示原則**:
  - 長大なドキュメントではなく、「1画面・1プロンプト」に収まる制約（1枚企画書フォーマット）を課す。
  - 必須構成要素を以下の5点に厳選する：
    1. **ゲームの核（一文）**: 「〇〇を爽快に破壊する」「〇〇の駆け引きを楽しむ」（20文字以内）
    2. **基本画面レイアウト**: ASCIIアートまたはブロック図でプレイヤーの視野を確定
    3. **コアループ（3ステップ）**: 課題提示 → 操作実行 → 報酬獲得
    4. **独自性**: 他作との決定的な違い1点
    5. **ターゲット層とスキルキャップ制約**: 想定プレイヤー、同時入力数上限、認識負荷上限、検証仮説
- **アンチパターン**:
  - 世界観設定や長大なバックストーリー、膨大なアイテム一覧を先に書き連ね、「どんな画面で何をして遊ぶのか」が伝わらない企画出力。
- **AIレビュー用チェックリスト**:
  - [ ] A4用紙1枚（またはスクロールなしの1画面）で、ゲームの全容と主操作が一目で把握できるか？
  - [ ] 画面レイアウトの概略図（ASCII等）が含まれ、プレイヤーの視界が具体化されているか？

### #02 企画の核（コアコンセプトの死守）
- **核心**: 企画にはブレてはならない「芯（核）」が不可欠。「このゲームは〇〇を楽しむゲームである」と一言で言い切れる核が定まっていないと、制作途中で様々なアイデアに振り回され、平凡で焦点の合わない作品になる。
- **Core Skill**: **イミュータブル・コアバリュー（不変の主目的）の策定**
- **AIへの実装・指示原則**:
  - プロジェクト冒頭で「コアコンセプト（核となる単一の動詞・感情体験）」を1行の不変定数（Constant）として定義する。
  - 以降の機能追加・仕様策定プロンプトにおいて、「この新機能は、定義されたコアコンセプトを直接強化するか？」をAI自身に事前評価させ、関連性が薄い場合は実装を却下（Reject）する。
- **アンチパターン**:
  - 「クラフトもできて、オープンワールドで、カード対戦もできて、重厚な物語もある」といった、核が存在しないバズワードの寄せ集め。
- **AIレビュー用チェックリスト**:
  - [ ] ゲームの最も面白い瞬間を一文（20文字以内）で端的に言い切れているか？
  - [ ] 実装されているすべてのシステムが、その一文の体験を支えるために直結しているか？

### #03 アイデアは引き算（要素の削ぎ落としと統合）
- **核心**: 面白そうなアイデアを足し続けると、操作が煩雑になりゲームが破綻する。優れた設計とは、要素を増やすことではなく、削ぎ落として残った本質を磨くこと、あるいは1つの要素に複数の役割を持たせる（多目的化）こと。
- **Core Skill**: **メカニクス・プルーニング（機能剪定と多目的化）**
- **AIへの実装・指示原則**:
  - 新しいギミックを追加したい場合、既存のルールを増やすのではなく「既存のオブジェクトやアクションに新しい役割を兼任させる（多目的化）」よう制約する。
  - 機能提案プロンプトの出力時に、必ず「この機能を入れる代わりに削除できる、または簡素化できる既存機能は何か？」を同時に出力させる。
- **アンチパターン**:
  - 課題が生じるたびに新しい操作ボタンや特殊ゲージ、専用ルールを継ぎ足し、UIと入力体系を複雑化させる設計。
- **AIレビュー用チェックリスト**:
  - [ ] 単一のシステムやボタンが、攻撃と移動、攻撃と防御など複数の役割を美しく兼ね備えているか？
  - [ ] 削ってもゲームの本質的な面白さが損なわれない「余分な肉」が放置されていないか？

---

### #04 アイデアは組み合わせ（既存要素の交差設計）
- **核心**: 「完全な無から生み出されるまったく新しいアイデア」など存在しない。アイデアとは常に「既存の要素と既存の要素の、誰も試していない組み合わせ」。親しみのあるルール同士を掛け合わせることで、直感的に理解しやすく、かつ新鮮な遊びが生まれる。
- **Core Skill**: **クロスドメイン・シンセシス（2要素の直交合成）**
- **AIへの実装・指示原則**:
  - 企画ブレインストーミング時、「広く認知されたメカニクスA」と「別ジャンルのメカニクスB」を2つ明示的に指定し、その接点から生まれる化学反応のみを設計させる（例：落ち物パズル × 打ち上げ花火、ピンボール × ハック＆スラッシュ）。
  - 既存の文脈を半分残すことで、チュートリアルを最小限にし、プレイヤーが直感的にルールを把握できるようにする。
- **アンチパターン**:
  - 誰も理解できない奇抜すぎる独自用語や未知のルール体系を構築し、ルールの説明だけでプレイヤーを疲弊させる。
- **AIレビュー用チェックリスト**:
  - [ ] 既存の有名な遊びや日常の直感（重力、反射、パズル等）が土台として機能しているか？
  - [ ] 2つの要素が単に並列に並んでいるだけでなく、互いのルールを強化し合っているか？

---

### #05 仕様書の書き方（実装者の迷いをゼロにする）
- **核心**: 仕様書は文学作品やポエムではない。「適度に」「いい感じに」「かっこよく」といった曖昧な言葉は実装現場の混乱と手戻りを生むだけ。誰が読んでも同一の挙動を再現できるよう、入力・条件分岐・例外処理・フレーム単位の数値を明確に定義する。
- **Core Skill**: **決定論的仕様定義（Deterministic Spec Definition）**
- **AIへの実装・指示原則**:
  - 自然言語による曖昧な指示を禁止し、**状態遷移図（State Machine）**、**入力マトリクス**、**数値定義表（Config/JSON）**の形式で仕様を出力させる。
  - 「ボタンを同時押しした場合はどちらを優先するか」「画面端に到達した座標はどうクランプされるか」「HPが0と同時に攻撃が当たった場合はどうなるか」といった境界条件（Edge Cases）を必ず網羅させる。
- **アンチパターン**:
  - 「敵が近づいたら怒って突進してくる」といった主観的・感情的な記述で済ませ、感知距離や突進速度、硬直時間の定義を丸投げする。
- **AIレビュー用チェックリスト**:
  - [ ] すべてのアクションの「発生フレーム」「持続」「硬直」「移動量」が数値として定義されているか？
  - [ ] 例外的な操作や極端な状況における優先順位（Priority）が明確に定義されているか？

### #06 最初から完成形を見据える（手戻りゼロの逆算設計）
- **核心**: 「作りながら考える」は手戻りとリテイクの温床になり、工数を無限に浪費する。企画の最初の段階で、最終的なタイトル画面、ゲームループ、ステージ数、エンディングの演出まで、頭の中で完成品の映像を完全に組み立ててから着手すべき。
- **Core Skill**: **エンドステート・バックキャスティング（完成形からの逆算）**
- **AIへの実装・指示原則**:
  - 初期モックアップを実装する前に、「画面遷移マップ（Scene Architecture）」と「全体の進行チャート（Progress Table）」を先に確定させる。
  - 途中での仕様追加（Feature Creep）を厳禁とし、最初に描いた青写真のスケール内にすべてのコンポーネントが収まるようトップダウンで工数とデータ構造を統制する。
- **アンチパターン**:
  - 基礎の動詞が決まっていない段階でアセットや細かい背景を作り始め、後から「画面に収まらない」「ゲームのテンポと合わない」と判明して破棄する。
- **AIレビュー用チェックリスト**:
  - [ ] ゲーム開始からゲームオーバー/クリア画面までの遷移フローが完全に閉じているか？
  - [ ] 後から大規模なアーキテクチャ変更が発生しないよう、最終形に必要なデータ構造が最初から網羅されているか？

### #07 ターゲット層の固定（万人受けの幻想の破棄）
- **核心**: 「誰にでも楽しんでもらえるゲーム」を作ろうとすると、コア層には物足りず、初心者には難しすぎる中途半端な作品になる。『星のカービィ』が徹底して初心者に寄り添って作られたように、ターゲットとするプレイヤーの熟練度を明確に固定しなければならない。
- **Core Skill**: **ペルソナ・スキルキャップ制約（Target Proficiency Boundary）**
- **AIへの実装・指示原則**:
  - 前提条件として「想定プレイヤーのスキルレベル」を厳密に定義する（例：「コントローラーの2ボタン同時押しが苦手な完全初心者」または「15フレーム以内の目押し反応ができるアクション経験者」）。
  - 設定したターゲットが「直感的に実行できる入力数」「1画面内で同時に認識できる敵の数」を上限値（Constraint）としてパラメータに組み込ませる。
- **アンチパターン**:
  - 初心者向けのアクションを謳いながら、ダッシュジャンプやシビアなフレーム回避を必須テクニックとして要求する難易度の破綻。
- **AIレビュー用チェックリスト**:
  - [ ] ターゲット層のスキル水準を超えた、理不尽・複雑な操作が進行の必須条件になっていないか？
  - [ ] 操作難易度と画面内の情報量が、設定したペルソナの許容量に収まっているか？

---

### #08 プロトタイプの目的を絞る（検証のための使い捨てコード）
- **核心**: プロトタイプは製品の一部ではない。「この操作、このアイデアは本当に面白いのか？」という仮説を最速で検証するためだけの実験台。グラフィックや凝った演出は一切入れず、検証が終わったら気兼ねなく捨てられる簡素な作りに徹するべき。
- **Core Skill**: **ハイポセシス・ドリブン・モック（仮説検証型プロトタイピング）**
- **AIへの実装・指示原則**:
  - スプライト画像や複雑なUI、音響の実装を明示的に禁止し、幾何学図形（四角・円・ワイヤーフレーム）のみで構築させる。
  - 「検証したい仮説（例：ジャンプの溜め時間と飛距離の比率は気持ちいいか？）」を1点だけ定義し、その仮説に関係のないシステムは一切コードに含めさせない。
- **アンチパターン**:
  - 面白いかどうかも分からない未検証のルールのために、美麗なアセットや複雑なパーティクル演出を作り込んで時間を浪費する。
- **AIレビュー用チェックリスト**:
  - [ ] プロトタイプが「単一の問い」に答えるためだけの最小コード（Minimal Viable Code）になっているか？
  - [ ] 仮説が否定された場合、未練なく破棄して作り直せる構造になっているか？
